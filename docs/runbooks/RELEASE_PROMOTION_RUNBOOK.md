# Exact-candidate release promotion

## Preconditions

Promotion is a protected, manual operation on the canonical repository and
`main`. Freeze the candidate tag, source commit, full source tree, release
manifest, universal PKG, image, SBOM, migration/catalog set, KMS/Platform Auth
reports, and hardware reports. Compute SHA-256 digests before opening the
promotion record. Promotion never rebuilds or repackages a qualified artifact.

The required CI lanes are exactly:
`postgres-authority-16`, `postgres-authority-17`, `postgres-integration`,
`browser-e2e`, `p0b-live-process`, and `test`.

## Execution sequence

1. Capture the GitHub run and jobs JSON for the canonical successful push run.
   Validate the exact source and lane inventory:

   ```sh
   node scripts/release/ci-preflight.mjs github \
     /secure/evidence/ci-run.json /secure/evidence/ci-jobs.json \
     <40-char-source-sha> Torutesu/AIagentpass \
     > /secure/evidence/ci-preflight.json
   ```

   Require completed `success`, `main`, the canonical workflow path, exact
   six-lane inventory, unique job IDs, and one source SHA. A missing or
   paginated jobs response is a failure.

2. Validate the source-bound KMS and Platform Auth reports with the commands
   in [`KMS_POSTGRES_QUALIFICATION_RUNBOOK.md`](KMS_POSTGRES_QUALIFICATION_RUNBOOK.md).
   Require `passed`/`qualified: true`; reject `not_run`, failed, non-canonical,
   secret-bearing, or mismatched source/tree/run/job/deployment evidence.

3. Verify the signed release manifest and staged macOS candidate using
   [`MACOS_RELEASE_NOTARIZATION_RUNBOOK.md`](MACOS_RELEASE_NOTARIZATION_RUNBOOK.md).
   The package digest is calculated after stapling and must match every
   manifest, hardware report, and promotion summary.

4. Scan the exact downloaded candidate and evidence archive. For a release
   tree, use the repository scanner so PKG contents are expanded and opaque
   archives are not silently skipped:

   ```sh
   node scripts/release/ci-preflight.mjs artifact-scan \
     /secure/candidate /secure/evidence/artifact-scan.json
   node scripts/release/ci-preflight.mjs secret-scan \
     /secure/candidate /secure/evidence
   ```

   Require clean output, no symlinks/hardlinks, no secret markers, and exact
   artifact names. Never scan an evidence file against itself; exclude it only
   through the scanner's explicit `--exclude=<relative-path>` option.

5. Supply one externally reviewed, canonical evidence index to the protected
   promotion workflow. The index is operator input, not generated by CI, and
   must contain exactly these bindings:

   - `candidate`: exact `candidate_id`, source commit/tree, release-manifest
     digest, candidate artifact name, and final `artifact_sha256`;
   - `runs`: exact release, qualification, canonical CI, and staging
     `run_id`/`run_attempt`/`job_id` values;
   - `artifacts`: the exact candidate artifact name/digest and the successful
     release job that produced it;
   - `reviewer`: reviewer ID, signed `report_sha256` digest, candidate/source/artifact
     and staging-evidence bindings, plus `reviewed_at` and a future
     `expires_at` no more than 30 days after review;
   - `rollback`: candidate/source/artifact, deployment/current revision,
     rollback target, staging run/job, rollback evidence digest, and an
     executed `status: passed`, `tested: true` result.

   The workflow rejects a missing, non-canonical, expired, substituted, or
   incomplete index before release creation. It writes the validated index to
   the release integrity evidence; it never fills missing fields with local
   timestamps, guessed IDs, or simulated results.

   Then project the reviewed cutover and traffic-rollback envelopes into the
   provider-neutral evidence contract:

   ```sh
   npm run release:cutover-evidence -- \
     /secure/evidence/staging-metadata.json \
     /secure/evidence/cutover.json \
     /secure/evidence/rollback.json \
     /secure/evidence/console-readiness.json \
     > /secure/evidence/deployment-evidence.json
   ```

   A missing rollback is `not_run`, never success. Then check the source-bound
   staging deployment/rollback evidence with. The metadata and Console
   readiness files must carry the exact same source commit/tree, image digest,
   deployment ID/current and rollback revisions, schema digest, and catalog
   digest; the gate also requires the binding's deployment identity and current
   promotion run/attempt/job:

   ```sh
   npm run release:deployment-gate -- \
     /secure/evidence/deployment-evidence.json \
     /secure/evidence/deployment-binding.json
   ```

   Require the gate to prove readiness and an executed rollback for the exact
   candidate before treating staging as qualified. The protected promotion
   workflow additionally consumes the retained canonical records through
   `AGENTPASS_STAGING_READINESS_JSON`, `AGENTPASS_STAGING_ROLLBACK_JSON`, and
   `AGENTPASS_STAGING_BINDING_JSON`, and runs:

   ```sh
   node scripts/release/staging-readiness.mjs verify \
     /secure/evidence/staging-readiness.json \
     /secure/evidence/staging-binding.json
   node scripts/release/staging-rollback.mjs verify \
     /secure/evidence/staging-rollback.json \
     /secure/evidence/staging-binding.json
   ```

   The workflow recomputes the final artifact and release-manifest digests,
   compares candidate/source/tree and the exact deployment/image/deployment
   digest, and supplies the current UTC time to both verifiers. Missing,
   `not_run`, failed, substituted, or expired readiness/rollback evidence is a
   promotion stop condition. Then check the staging drill and independent
   review sign-offs represented by the evidence index.
   Before dispatch, run the protected operator preflight in
   [`PROTECTED_OPERATOR_PREFLIGHT_RUNBOOK.md`](PROTECTED_OPERATOR_PREFLIGHT_RUNBOOK.md)
   and retain its canonical `status: "passed", qualified: true` result. Its
   candidate, source/tree, reviewer expiry, and rollback evidence must be the
   same records supplied to this promotion; a local pass or regenerated result
   is not a substitute for retained external evidence. Then dispatch the
   protected promotion workflow with distinct release, qualification, and
   canonical CI run IDs. Preserve the workflow result and published artifact
   list. After uploading `release-asset-roundtrip.json`, the workflow
   re-downloads that exact evidence asset, compares bytes, checks canonical
   JSON, and secret-scans it before publishing; a mismatch is a stop condition.

6. Promote traffic only after the workflow and operator checks pass. Record
   canary start/end, monitor owner, rollback target, and the first post-
   promotion readiness/audit snapshot.

## Mandatory STOP conditions

Set `STOP` and do not waive it in a release ticket when any item is true:

- source SHA/tree, manifest, PKG, image, SBOM, migration, qualification, or
  hardware digest differs or is missing;
- any canonical CI lane is absent, duplicated, skipped, failed, `not_proven`,
  or bound to another run/job;
- any required report is stale, non-canonical, contains a secret, or lacks the
  exact source/tree/run/job/deployment binding;
- a signer purpose is missing, shared, disabled, stale, wrong-version,
  local/file-backed, or lacks canary/lifecycle/response-loss proof;
- PostgreSQL role/RLS/0047, TLS identity, checksum, backup/PITR/restore,
  failover, or authority comparison is unproven;
- any promotion issuance is `reserved`, `uncertain`, or `rejected`, or would
  require blind retry, row deletion, down-migration, or rebuild;
- Developer ID, notarization `Accepted`, stapling, Gatekeeper, or both
  Apple-silicon and Intel/T2 same-digest reports are absent;
- revoke bound, staging recovery, alerting, or independent-review closure is
  missing; or
- deployment readiness/rollback evidence is absent, `not_run`, failed, or
  bound to another source, manifest, artifact, deployment digest, or run; or
- a critical/high finding or required security retest remains open.

Record the stable reason code, affected digest, owner, and replacement action.
Do not edit a failed evidence file into a pass.
