# Staging deployment readiness contract

The complete cross-scenario evidence contract is in
[STAGING_DRILL_EVIDENCE_CONTRACT.md](STAGING_DRILL_EVIDENCE_CONTRACT.md).
This document describes the readiness-specific projection; it must be read
with that contract for failover, PITR, signer-outage, recovery, independent
observer, and measured SLO/RPO/RTO requirements.

This runbook defines the provider-neutral evidence contract for staging. It
does not add or alter Cloud API, Console, human-auth, WebAuthn, session, or
authorization behavior. The deployment adapter collects the existing health
and operational observations, then emits one canonical JSON record for the
release gate to verify.

## Required binding

The binding file must contain exactly `candidate`, `deployment`, and
`rollback_target` objects. Each candidate binds `candidate_id` to the exact
`artifact_sha256` (`release-pkg-sha256-v1-<artifact_sha256>`) and carries the
release-manifest digest, source commit, and full source tree. Each deployment
binds the staging environment, service, deployment ID, revision, image digest,
and deployment digest. The rollback target has the same complete identity and
must use a different revision in the same staging service/deployment.

Do not copy values from an unverified provider response. Populate the binding
from the signed release manifest, immutable artifact, exact source checkout,
and the deployment's measured identity.

## Evidence requirements

`staging-readiness.mjs` requires an exact, canonical JSON object with:

- a current, non-expired `issued_at`/`expires_at` window no longer than 24
  hours;
- exact candidate/source/tree, artifact, manifest, image, and deployment
  digests;
- four readiness checks: `application`, `database_schema`, `audit_path`, and
  `console`; every check must be an observed `ready` result for qualification;
- a bounded canary with 1–50% traffic, at least one request, all requests
  successful, zero errors, and `expected: "healthy"` equal to
  `observed: "healthy"`;
- a completed drain from a different revision to the new revision, with new
  work stopped, `drained: true`, and zero in-flight work; and
- a known, ready rollback target bound to its own candidate and deployment
  identity.

Readiness is not complete until the same protected execution envelope also
contains the fixed `canary`, `drain`, `rollback`, `failover`, `pitr`,
`signer_outage`, and `recovery` scenario records. Every record must carry the
exact candidate/source/tree, artifact/image/schema/catalog/database-schema
digests, a unique execution ID, an independently verifiable observer, and the
scenario's measured SLO/RPO/RTO. The verifier must derive the aggregate status;
`qualified: true` or a copied provider status is never sufficient.

The record contains `evidence_sha256`, calculated over the canonical record
without that field. Unknown fields, accessors, arrays in place of objects,
symlink/hardlink evidence files, noncanonical JSON, digest substitution,
failed checks, and `not_run` checks are rejected.

Verify the retained evidence from the protected checkout:

```sh
node scripts/release/staging-readiness.mjs verify \
  /secure/evidence/staging-readiness.json \
  /secure/evidence/staging-binding.json \
  --now=2026-08-20T12:00:00.000Z
```

The command must exit zero and emit `status: "passed"` and
`qualified: true`. A non-zero result is `STOP`; do not edit failed evidence or
replace it with a simulated pass. The `--now` option is for deterministic
replay and tests; normal operations use the host UTC clock.

Readiness evidence is local contract evidence until the real staging provider
execution, image identity, database measurement, canary metrics, drain
timeline, and retained run/job record are independently verified. A focused
test pass does not close those external gates.

The same boundary applies to failover, PITR, signer outage, and recovery. A
local/mock/fixture/sandbox result, `not_run`, `not_proven`, stale, or
self-reported observer record is a hard stop and must remain so in the
retained evidence.

## Promotion handoff

The protected promotion workflow consumes the canonical records from the
repository variables `AGENTPASS_STAGING_READINESS_JSON`,
`AGENTPASS_STAGING_ROLLBACK_JSON`, and `AGENTPASS_STAGING_BINDING_JSON`.
These variables are operator-managed retained evidence, not generated by the
promotion runner. The binding must be prepared from the signed release
manifest, the final PKG bytes, and the already-qualified staging deployment
record. The workflow independently recomputes the manifest and PKG digests,
compares the deployment ID, revision, image digest, and deployment digest, and
then invokes both staging verifiers using the current UTC time.

The workflow stops before release creation or publication when any record is
missing, non-canonical, expired, `not_run`, `failed`, or not exactly bound to
the candidate/source/tree, artifact, or staging deployment. Verified
`staging-readiness.json`, `staging-rollback.json`, and `staging-binding.json`
are retained in release integrity evidence and secret-scanned before upload.
