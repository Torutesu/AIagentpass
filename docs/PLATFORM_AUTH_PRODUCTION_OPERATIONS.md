# Platform authenticator production operations

Status: deployment and operations contract. This document does not claim that
local tests, a configuration report, or a development adapter is production
qualification.

## Boundary and wiring

Platform promotion is a global platform operation. It must not fall back to an
organization `owner`/`admin` role, a bearer token, a browser cookie, or a
forwarded certificate header. The deployment adapter must inject four
independent checks into `createPlatformAuthenticator`:

1. `platform_role` from the platform principal provider;
2. the authenticated TLS socket peer with the pinned SHA-256 fingerprint and
   SPIFFE URI;
3. a deployment-owned workload identity verifier bound to the expected
   workload ID, audience, operation, and mTLS fingerprint; and
4. a consumed, operation- and principal-bound Recent WebAuthn proof.

The application authenticator accepts verifier functions and public identity
metadata, not private keys or raw provider claims. TLS private keys, client CA
material, workload-provider credentials, database credentials, and
identity-provider credentials belong in the approved secret manager or managed
ingress. They must never be requested from an operator, placed in a shell
command, logged, or copied into qualification evidence.

The workload verifier's successful result is a closed envelope with exactly
`verified`, `workload_id`, `audience`, `expires_at` (a future integer epoch in
milliseconds), and `mtls_fingerprint256` (the non-zero SHA-256 fingerprint of
the authenticated peer). Both expiry and fingerprint are mandatory; omitting
either field is rejected. This prevents a provider adapter from silently
creating a non-expiring or non-peer-bound Platform identity.

The HTTP promotion boundary repeats this validation after dependency
composition. A custom or accidentally substituted authenticator therefore
cannot bypass the short-lived workload and peer-binding requirements by
returning a structurally incomplete authorization object.

Platform decisions are recorded as secret-free, append-only audit events. The
event id is generated by the service, while the caller-provided idempotency
key identifies the logical event. Retrying the same logical event with the
same key and unchanged request/details returns the original event identity;
changing any protected field is an idempotency conflict.

The deployment must also inject a durable `platformAuditAppender`. Enabling the
promotion route without this appender is rejected at startup; an operation is
not considered successful if its secret-free audit event cannot be persisted.

## Production environment contract

Run the secret-free preflight from the same sanitized environment used by the
Cloud process:

```sh
node scripts/qualification/validate-platform-auth-config.mjs \
  > /secure/qualification/platform-auth-config.json
```

The command reports only pass/fail and reason codes. It never prints an
environment-variable value. A non-zero exit is a deployment blocker.

| Variable | Required | Contract |
| --- | --- | --- |
| `AGENTPASS_CLOUD_PROFILE` | yes | `hosted`; evaluation mode is forbidden |
| `AGENTPASS_PLATFORM_AUTH_ENABLED` | yes | literal `true` |
| `AGENTPASS_CONSOLE_ORIGIN` | yes | HTTPS origin, no credentials/query/fragment |
| `AGENTPASS_WEBAUTHN_RP_ID` | yes | RP ID that is the console host or its parent domain |
| `AGENTPASS_PLATFORM_MTLS_FINGERPRINT256` | yes | pinned 32-byte colon-delimited SHA-256 fingerprint |
| `AGENTPASS_PLATFORM_MTLS_SPIFFE_ID` | yes | expected non-empty `spiffe://` URI |
| `AGENTPASS_PLATFORM_WORKLOAD_ID` | yes | exact workload identity; must equal the pinned SPIFFE ID |
| `AGENTPASS_PLATFORM_WORKLOAD_AUDIENCE` | yes | exact audience accepted by the workload verifier |
| `AGENTPASS_PLATFORM_PRINCIPAL_PROVIDER` | yes | deployment provider identifier; no local fixture mode |
| `AGENTPASS_PLATFORM_WORKLOAD_PROVIDER` | yes | deployment verifier identifier; no local fixture mode |
| `AGENTPASS_PLATFORM_WEBAUTHN_PROVIDER` | yes | durable WebAuthn verifier identifier; no local fixture mode |
| `AGENTPASS_PLATFORM_REQUIRED_ROLE` | no | defaults to `platform_operator` |
| `AGENTPASS_PLATFORM_RECENT_AUTH_HEADER` | no | defaults to `agentpass-platform-recent-auth`; header name only |

The existing hosted PostgreSQL, console, WebAuthn, KMS, and identity-provider
settings remain mandatory through the normal hosted runtime profile. This
preflight does not inspect those values or validate private material; the
hosted runtime readiness and provider-specific qualification gates remain
authoritative for them.

## Safe failure behavior

| Condition | HTTP result | Operational meaning |
| --- | --- | --- |
| Handler is not installed or the feature route is disabled | `404 not_found` | Route is not exposed; this is not a successful promotion path. |
| Any principal, mTLS, workload, or WebAuthn verifier is missing/unavailable, or the handler cannot produce a bounded response | `503` with a generic platform-unavailable code | Fail closed; remove the candidate from traffic and repair configuration/dependency health. |
| Configured route receives no/invalid proof or invalid client identity | `401` | Authentication failed; do not substitute organization auth. |
| Authenticated principal lacks the required platform role | `403` | Authorization denied; organization roles do not change the result. |
| Promotion is in progress, uncertain, or rejected | `409` | Reconcile durable state; never blindly re-sign or rebuild. |

The public response must not contain certificates, private keys, provider
claims, WebAuthn assertions, database URLs, or secret-manager responses.
Forwarded client-certificate headers are not an authentication source. Recent
WebAuthn is operation-bound, member-bound, consumed exactly once, and rejected
when older than five minutes or more than thirty seconds in the future.

## Deployment and incident procedure

1. Render the immutable candidate and deployment metadata. Do not render
   secret values into the manifest.
2. Run the preflight above in a sanitized process environment and store the
   redacted JSON report with the candidate digest.
3. Confirm the ingress verifies client certificates, passes the authenticated
   TLS socket to the application, and does not rely on a forwarded certificate
   header.
4. Confirm the workload verifier is deployment-owned and checks audience,
   expiry, operation, and mTLS fingerprint. Confirm WebAuthn consumes the
   exact challenge for the exact platform principal and operation.
5. Probe one approved operation through the protected path, then verify the
   durable state and audit event. A `404` or `503` is a failed readiness
   result, not a degraded success.
6. During an outage, stop new promotion traffic, preserve durable `uncertain`
   state, and reconcile by provider receipt/ledger lookup. Never retry a
   provider call solely because an HTTP response was lost.

## Rotation runbook

Rotation is a controlled deployment and must be evidenced with old/new public
identifiers and timestamps only. Do not place secret values in the report.

### mTLS client identity

Issue the replacement certificate and validate its chain, validity window,
SPIFFE URI, and fingerprint out of band. The current authenticator pins one
fingerprint, so use a coordinated drain or an explicitly reviewed ingress/
adapter overlap; do not overwrite the active pin while traffic is flowing.
Deploy the new pin, run the protected probe, confirm the new fingerprint is
observed, drain the old identity, and revoke the old certificate. If the probe
fails, stop traffic and restore the previous public pin before retrying.

### Workload identity

Create the replacement provider binding and authorize it for the exact
audience. Keep the workload ID stable when possible. If it must change, update
the SPIFFE pin and workload ID atomically, run the preflight, then verify the
new binding to the authenticated mTLS fingerprint. Disable the old binding
only after the new probe and audit event are confirmed.

### Platform principal and WebAuthn

Rotate provider credentials through the secret manager's versioned reference;
do not copy credentials into an environment dump. Enroll or revoke a human
platform operator's WebAuthn credential through the durable ceremony, verify a
fresh operation-bound challenge, and retain only public metadata and an audit
reference. Revoke the old principal or credential after the new path passes.

### Rollback

Rollback is allowed only to the previous immutable, source-bound candidate and
matching public configuration. Never rebuild or reuse a revoked private key.
After rollback, run the same preflight and protected probe; a `503` remains a
failed rollback and requires traffic drain.

## Qualification and evidence

The qualification contract is [PLATFORM_AUTH_QUALIFICATION.md](PLATFORM_AUTH_QUALIFICATION.md).
The local gate proves metadata shape and negative configuration cases only.
Production qualification additionally requires protected ingress mTLS, the
real workload identity provider, durable PostgreSQL/WebAuthn consumption, two
independent Cloud instances, provider/KMS behavior, rotation, response-loss
reconciliation, and secret scans. None is satisfied by the local script or
unit tests.
